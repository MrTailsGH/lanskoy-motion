# Почему рендер идёт 40 минут вместо четырёх

Документ для Claude, который ведёт чужой проект с покадровым рендером HTML в
видео. У нас 1500 кадров собираются за 1,5–3 минуты, у вас за 40. Разница не в
железе — она почти всегда в четырёх вещах, и ниже сказано, как их найти
измерением, а не догадками.

**Исходные числа.** 1500 кадров / 40 минут = **0,63 кадра в секунду**, то есть
1,6 секунды на кадр. Для статичной HTML-сцены 1080×1920 это в двадцать пять раз
медленнее нормы. Столько стоит либо перезапуск браузера на каждом кадре, либо
ожидание чего-то, чего можно не ждать.

## Наши замеры для ориентира

Одна и та же сцена, 1080×1920, 30 fps, 1374 кадра:

| Способ | Скорость | Время |
|---|---|---|
| Playwright, скриншот на кадр, без оптимизаций | 1,5 кадр/с | ~15 минут |
| Remotion + headless shell, слабый контейнер | 7 кадр/с | 3 мин 15 с |
| Remotion + headless shell, обычный раннер CI | 16 кадр/с | 85 секунд |

Кодирование PNG-последовательности в H.264 — ещё 37 секунд, один раз в конце.

**Вывод для ориентира:** нормальная цель — не меньше 5 кадров в секунду на любой
машине. Если у вас 0,6, дело не в тонкой настройке, а в архитектурной ошибке.

---

## Шаг 0. Измерить, где уходит время

До любых правок нужны три числа. Без них оптимизация превращается в перебор.

Положите рядом со сценой `bench.mjs` и запустите:

```js
// bench.mjs — сколько стоит один кадр и из чего эта стоимость складывается
import {chromium} from 'playwright';

const SCENE = process.argv[2] ?? 'scene.html';
const N = 60;                                  // хватит шестидесяти кадров

const b = await chromium.launch({args: ['--no-sandbox', '--force-device-scale-factor=1']});
const page = await b.newPage({viewport: {width: 1080, height: 1920}, deviceScaleFactor: 1});

let t = Date.now();
await page.goto('file://' + new URL(SCENE, `file://${process.cwd()}/`).pathname);
await page.waitForFunction(() => document.fonts?.status === 'loaded');
console.log('загрузка страницы:', Date.now() - t, 'мс — платится один раз');

// чистая стоимость seek без скриншота
t = Date.now();
for (let i = 0; i < N; i++) await page.evaluate((f) => window.seek?.(f / 30), i);
const seekMs = (Date.now() - t) / N;

// стоимость скриншота без seek
t = Date.now();
for (let i = 0; i < N; i++) await page.screenshot({type: 'png'});
const shotMs = (Date.now() - t) / N;

console.log('seek на кадр:      ', seekMs.toFixed(1), 'мс');
console.log('скриншот на кадр:  ', shotMs.toFixed(1), 'мс');
console.log('потолок скорости:  ', (1000 / (seekMs + shotMs)).toFixed(1), 'кадр/с');
await b.close();
```

Дальше читаете результат так:

| Что видно | Что это значит | Куда идти |
|---|---|---|
| потолок 10+ кадр/с, а рендер даёт 0,6 | время уходит **между** кадрами | причина 1 и 2 |
| скриншот больше 150 мс | дорогая отрисовка | причина 5 и 6 |
| seek больше 50 мс | тяжёлый пересчёт сцены | причина 7 |
| загрузка страницы больше 3 с | сеть или шрифты | причина 8 |

Не пропускайте этот шаг. Половина «медленных рендеров» лечится одной строкой,
и без замера вы эту строку не найдёте.

## Причина 1. Браузер или страница поднимаются на каждом кадре

**Самая частая и самая дорогая.** Выглядит в коде так:

```js
for (let f = 0; f < frames; f++) {
  const browser = await chromium.launch();       // ← 800–1500 мс каждый кадр
  const page = await browser.newPage();
  await page.goto(url);                          // ← ещё 200–600 мс
  await page.screenshot({path: `frame-${f}.png`});
  await browser.close();
}
```

Ровно это даёт 1,6 секунды на кадр. Браузер и документ поднимаются **один раз**
за весь рендер, дальше меняется только время:

```js
const browser = await chromium.launch({args: ['--no-sandbox']});
const page = await browser.newPage({viewport: {width: 1080, height: 1920}, deviceScaleFactor: 1});
await page.goto(url);
await page.waitForFunction(() => document.fonts?.status === 'loaded');

for (let f = 0; f < frames; f++) {
  await page.evaluate((n) => window.seek(n / 30), f);
  await page.screenshot({path: `frames/f-${String(f).padStart(5, '0')}.png`});
}
await browser.close();
```

Разница — от двадцати до пятидесяти раз. Если в коде есть `launch()` или
`goto()` внутри цикла по кадрам, дальше можно не читать: сначала это.

## Причина 2. Сцена не является функцией времени

Если картинка живёт на CSS-анимациях, `requestAnimationFrame`, таймерах или
теге `<video>`, то покадровый захват вынужден **ждать**, пока сцена сама
доедет до нужного момента. Отсюда `waitForTimeout` в цикле — и минуты из
воздуха. Хуже того, результат недетерминирован: один и тот же кадр выходит
разным от запуска к запуску.

**Контракт, который надо ввести.** Сцена не анимируется сама. Она умеет одно:
показать своё состояние в момент `t`.

```js
window.META = {FPS: 30, DUR: 46.03, FRAMES: 1381};

window.seek = function (t) {
  // ни одного таймера, ни одной CSS-анимации, ни одного await —
  // чистая функция: то же t даёт тот же кадр всегда
  card.style.opacity   = fade(t, 2.0, 0.3);
  value.textContent    = Math.round(134000 * ramp(t, 4.0, 0.55));
  // …
};
window.seek(0);
```

Что уходит из сцены при переводе на этот контракт: `@keyframes`, `transition`,
`setTimeout`, `setInterval`, `requestAnimationFrame`, автовоспроизведение видео.
Всё это заменяется чистым расчётом от `t`.

Что вы получаете, кроме скорости: возможность снять любой кадр за секунду
(`seek(23.4)` и скриншот), покадровое сравнение двух версий и отсутствие
«иногда отрисовалось, иногда нет».

Если в проекте React — это Remotion и есть, там контракт тот же
(`useCurrentFrame()`), только не надо ломать его собственными таймерами.

## Причина 3. Кадры считаются в один поток

Кадры независимы, значит их можно считать параллельно. Remotion делает это
сам ключом `--concurrency`, по умолчанию берёт половину ядер:

```bash
npx remotion render src/index.ts Comp out/frames --sequence --image-format=png \
  --concurrency=$(nproc)
```

Если рендер свой, на Playwright — откройте N страниц в одном браузере и
раздайте им кадры по остатку от деления. Больше, чем ядер, ставить бессмысленно:
упрётесь в память и станет медленнее.

Честный потолок: ускорение примерно в 0,7 × число ядер. На четырёх ядрах — раза
в три.

## Причина 4. Полный Chrome вместо headless shell

Обычный Chrome тянет за собой то, что рендеру не нужно: GPU-процесс, службы,
расширения. Для покадрового захвата нужен `headless_shell` — облегчённая
сборка, она и быстрее поднимается, и меньше ест.

```bash
CHROME=$(ls -d /opt/pw-browsers/chromium_headless_shell-*/chrome-linux/headless_shell | tail -1)
npx remotion render … --browser-executable="$CHROME"
```

Заодно флаги, которые мы держим для стабильности картинки, а не скорости —
но без них кадры отличаются от машины к машине:

```
--force-device-scale-factor=1  --font-render-hinting=none
--disable-lcd-text  --hide-scrollbars  --no-sandbox
```

`--disable-lcd-text` обязателен: субпиксельное сглаживание даёт цветную бахрому
на буквах, которую потом видно в H.264.

## Причина 5. Скриншот дороже, чем нужно

Три частые ошибки, каждая стоит десятки процентов:

**`deviceScaleFactor: 2`.** Кадр считается в четыре раза большем разрешении и
потом сжимается. Если итог 1080×1920, ставьте 1 и рисуйте сцену сразу в целевом
размере.

**`fullPage: true`.** Заставляет браузер пересобирать layout всей страницы.
Для кадра фиксированного размера не нужен никогда.

**PNG на черновиках.** PNG жмётся долго. Пока смотрите тайминг и композицию,
берите JPEG — он в разы быстрее, а разницы на превью не видно:

```bash
npx remotion render … --image-format=jpeg --jpeg-quality=90   # черновик
npx remotion render … --image-format=png                      # финал
```

## Причина 6. Дорогие эффекты на всю площадь кадра

Вот что реально съедает миллисекунды на кадре 1080×1920, по убыванию:

| Эффект | Почему дорого | Чем заменить |
|---|---|---|
| `backdrop-filter: blur()` | пересчёт подложки каждый кадр | заранее размытая картинка-подложка |
| `filter: blur()` на большом слое | стоимость растёт с площадью | тень нарисовать в PNG один раз |
| `box-shadow` с большим radius на нескольких слоях | то же самое, умноженное на число слоёв | один слой с готовой тенью |
| `mix-blend-mode` поверх всего кадра | лишний проход композитинга | вжечь в фон заранее |
| SVG-фильтры (`feGaussianBlur`, `feTurbulence`) | считаются на CPU | PNG |
| огромные PNG, масштабируемые в кадре | ресемплинг каждый кадр | подготовить в нужном размере |

**Как найти виновника, не гадая.** Бинарный поиск: отключите половину слоёв,
замерьте `bench.mjs`, отключите половину оставшихся, снова замерьте. За четыре
итерации вы упрётесь в конкретный элемент. Обычно это один блок с тенью или
одно размытие на весь экран.

## Причина 7. Тяжёлый пересчёт внутри seek

Если `bench.mjs` показал больше 50 мс на seek, проблема в самой сцене:

- в `seek` создаются или удаляются DOM-узлы — **нельзя**, создавайте всё один
  раз при загрузке, а в `seek` только меняйте свойства;
- в `seek` читаются геометрия и размеры (`offsetHeight`, `getBoundingClientRect`,
  `getComputedStyle`) — каждое чтение после записи заставляет браузер
  пересчитывать layout синхронно. Замерьте один раз при старте и закешируйте;
- подбор размера шрифта в цикле («уменьшать, пока не влезет») — тоже один раз
  на титр, с кешем по тексту;
- сотни элементов, которым каждый кадр присваивается одно и то же значение —
  меняйте только то, что изменилось.

## Причина 8. Сеть в кадре

Шрифты с CDN, картинки по http, `@import` в CSS — всё это может опрашиваться
при каждом кадре или, хуже, отваливаться по таймауту. Правило простое: **сцена
должна рендериться с отключённой сетью**. Шрифты — локальные файлы, картинки —
рядом со сценой, никаких внешних ссылок.

Проверка честная: `--offline` или блокировка сети в контексте. Если сцена
собралась — зависимостей нет.

## Кодирование: отдельный шаг, а не часть рендера

Мы просим у рендерера PNG-последовательность и кодируем сами. Причина не в
скорости, а в качестве: встроенный кодировщик не даёт задать деблокинг и
адаптивное квантование, без которых на градиентах возвращаются полосы, а зерно
съедается. Замер PSNR против эталонного PNG: встроенный — 43,2 дБ, наша
строка — 44,6 дБ.

```bash
ffmpeg -y -framerate 30 -pattern_type glob -i 'out/frames/*.png' \
  -c:v libx264 -preset slow -crf 16 -pix_fmt yuv420p -profile:v high -level 4.2 \
  -x264-params "deblock=-1,-1:aq-mode=3:aq-strength=1.1" \
  -movflags +faststart -r 30 out/video.mp4
```

Это 37 секунд на 1381 кадр — один раз в конце, на общее время почти не влияет.
Для черновиков берите `-preset veryfast -crf 23`, будет впятеро быстрее.

Звук подклеивается отдельно и **без `-shortest` и без `apad`**:

```bash
ffmpeg -y -i out/video.mp4 -i voice.mp3 -c:v copy -c:a aac -b:a 192k out/final.mp4
```

Грабли, на которые мы наступили: `-af apad -shortest` вешает ffmpeg намертво.
Бесконечная тишина от `apad` не обрывается флагом `-shortest`, когда в цепочке
есть фильтр: процесс живёт, файл не растёт, ошибки нет.

## Ждать окончания рендера по числу кадров, а не по строчке в логе

Remotion печатает путь к папке кадров **при старте**. Наивная проверка
«появилась строка с путём — значит готово» считает рендер законченным на второй
секунде. Мы так однажды склеили ролик из 152 кадров вместо 1296 и заметили не
сразу.

```bash
WANT=$(node -e "…читаем DUR из сцены…")
HAVE=$(ls out/frames | wc -l)
[ "$HAVE" -ge "$WANT" ] || { echo "кадров $HAVE из $WANT — рендер не дошёл"; exit 1; }
```

## Порядок работ

1. Запустить `bench.mjs`, записать три числа. **Без этого дальше не идти.**
2. Убрать `launch()` и `goto()` из цикла по кадрам, если они там есть. Замерить снова.
3. Перевести сцену на контракт `window.seek(t)`, выкинуть CSS-анимации и таймеры. Замерить.
4. Включить параллельность по числу ядер. Замерить.
5. Перейти на `headless_shell`, поставить `deviceScaleFactor: 1`. Замерить.
6. Только теперь — бинарным поиском искать дорогой слой в самой картинке.
7. Кодирование вынести в отдельный вызов ffmpeg.

После каждого шага — замер. Если шаг не дал ускорения, откатите его: значит,
причина была не в нём, а лишняя сложность останется навсегда.

## Чего делать не нужно

**Гнаться за GPU.** В контейнерах и на CI видеокарты нет, всё считает
SwiftShader на процессоре. Флаги `--enable-gpu` там не помогают, а иногда
ломают отрисовку.

**Снижать разрешение.** Сначала добейтесь нормальной скорости в целевом
размере. Ролик на 800 пикселей по длинной стороне непригоден для публикации, и
вы просто отложите проблему.

**Ставить concurrency больше числа ядер.** Память кончится, начнётся своп, и
станет медленнее, чем в один поток.

**Оптимизировать кодирование.** Это 37 секунд из четырёх минут. Даже полный
отказ от него ничего не изменит, пока кадры считаются по 1,6 секунды.

## Как понять, что вы закончили

| Показатель | Норма |
|---|---|
| кадров в секунду | не меньше 5 на слабой машине, 15+ на нормальной |
| 1500 кадров | 1,5–5 минут вместе с кодированием |
| скриншот кадра | до 100 мс |
| seek | до 20 мс |
| два запуска подряд | побайтово одинаковые кадры |

Последняя строка важнее остальных. Детерминированный рендер можно чинить,
кешировать и сравнивать покадрово. Недетерминированный придётся пересматривать
глазами после каждой правки — а это дороже любых сорока минут.
